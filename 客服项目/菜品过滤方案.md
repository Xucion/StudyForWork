我建议采用混合方案，但优先级明确：

> 数据库负责硬过滤和事实校验，RAG/向量检索负责理解模糊口味和语义召回，最后由业务规则排序。

不能只用 RAG 推荐菜品，尤其涉及价格、上下架状态和过敏原时。

## 数据库适合处理什么

数据库处理结构化、必须准确的条件：

- 菜品是否起售；
- 最低价、最高价；
- 菜品分类；
- 辣度、甜度、油腻度；
- 荤素；
- 过敏原；
- 套餐人数；
- 库存；
- 当前门店可售范围。

例如用户说：

> 30 元以内，微辣，不要花生。

应该转换为确定性查询：

```
WHERE d.status = 1
  AND d.price <= 30
  AND p.spicy_level BETWEEN 1 AND 2
  AND NOT JSON_CONTAINS(p.allergens, '"花生"')
```

这些条件不应该交给向量相似度决定。即使某道菜向量匹配度很高，只要超过预算或含有花生，也必须排除。

## RAG适合处理什么

RAG适合处理无法简单结构化的表达，例如：

- “想吃点有锅气的”；
- “适合下雨天吃的”；
- “清爽但不要太寡淡”；
- “类似家常菜，但想有点新鲜感”；
- “适合健身后吃”；
- “想吃和水煮鱼风格接近但没那么辣的”。

这类需求可以通过菜品描述、标签、食材介绍和菜系知识进行语义召回。

例如为每道菜构建检索文档：

```
菜品：番茄牛腩
标签：酸甜、家常、热汤、牛肉、下饭
口感：浓郁、软烂
场景：天气冷、家庭用餐
描述：番茄汤底搭配炖煮牛腩，口味温和……
```

向量检索可以找到和“下雨天想吃点暖和的”语义接近的菜品。

但向量库里的价格和状态可能过期，因此召回后必须回数据库验证。

## 推荐链路

建议采用以下顺序：

```
用户自然语言
    ↓
LLM 提取结构化硬条件与语义偏好
    ↓
数据库执行硬过滤
    ↓
对剩余候选做向量语义匹配
    ↓
业务评分与多样性重排
    ↓
数据库再次确认价格和起售状态
    ↓
LLM 解释推荐理由
```

也可以根据候选规模调整顺序。

### 菜品数量较少

如果只有几十或几百个菜品：

```
数据库过滤 → Java 内存评分
```

暂时不需要向量数据库。为菜品维护标准化标签通常已经足够。

### 菜品数量较多

如果是多门店、上万菜品：

```
向量召回 Top 100
→ 数据库硬过滤
→ 排序 Top 5
```

但过敏原等高风险条件最好在向量召回前也加入元数据过滤，避免不合格候选进入后续链路。

## 条件分类很重要

可以把用户需求拆成三类：

| 类型     | 示例                         | 处理方式     |
| -------- | ---------------------------- | ------------ |
| 硬约束   | 30元以内、不要花生、必须素食 | 数据库过滤   |
| 软偏好   | 微辣优先、喜欢牛肉、少油更好 | 业务评分     |
| 语义需求 | 暖胃、有锅气、适合约会       | RAG/向量匹配 |

排序可以采用：

```
最终得分 =
  语义相似度 × 35%
+ 口味匹配度 × 30%
+ 价格匹配度 × 20%
+ 热度 × 10%
+ 多样性 × 5%
```

硬约束不参与评分，不满足就直接排除。

## 对当前项目的建议

当前项目的菜品数据规模不大，我不会第一版就引入完整 RAG。更合适的演进路线是：

1. 先给菜品增加标准化画像：
   - 辣度；
   - 甜度；
   - 油腻度；
   - 荤素；
   - 食材；
   - 标签；
   - 过敏原。
2. 使用数据库完成硬过滤和加权排序。
3. 积累真实查询，观察有多少需求无法被标签表达。
4. 再为菜品名称、描述、标签和适用场景生成向量，增加语义召回。
5. 无论是否使用 RAG，最终价格、状态和过敏原都必须回数据库校验。

所以最终结论是：

> 当前阶段以数据库检索为主；RAG是提升模糊语义理解和召回效果的增强层，不是菜品事实查询和安全过滤的替代品。
