**外卖智能客服与个性化菜品推荐 Agent**

# 问题

### 1. “滚动摘要与 Token 预算动态组装上下文”是什么意思？ 注释 1

模型都有上下文长度限制，不能每轮都把整个会话历史发送给模型。即使没有超过上限，历史过长也会增加费用、响应时间和噪声。

“滚动摘要”就是把较早的消息压缩成一段摘要，只保留最近消息原文。

例如原始对话已经有 100 条：

```
第1～80条 → 压缩成历史摘要
第81～100条 → 保留原始消息
当前问题 → 单独加入
```

最终发送给模型的内容类似：

```
系统提示词：
你是外卖客服……

历史摘要：
用户偏好微辣，预算30元以内，对花生过敏。
之前询问过订单A和订单B，当前主要讨论订单B。
订单B上次查询时正在配送。

最近消息：
用户：能不能换一个不带甜味的？
助手：可以，你更偏好肉类还是素菜？
用户：肉类。

当前问题：
那再推荐几个。
```

“Token 预算”是给不同内容预留长度，而不是固定取最近12条。例如模型最大支持一定上下文时，可以这样分配：

```
System Prompt        2,000 Token
工具定义              2,000 Token
结构化业务上下文       1,000 Token
历史摘要              2,000 Token
最近消息              5,000 Token
当前问题及输出预留      4,000 Token
```

组装流程通常是：

1. 加入不可删除的 System Prompt和安全规则；
2. 加入工具定义；
3. 加入当前问题；
4. 加入订单、推荐偏好等结构化状态；
5. 从最新到最旧加入历史消息；
6. 超出预算时停止加入；
7. 更早的历史使用摘要代替。

摘要不能作为价格、订单状态、过敏原等实时事实依据。它只能帮助理解上下文，关键业务事实仍需调用工具重新验证。

### 2. 双JWT鉴权如何实现？ 注释 2

AI客服涉及两种不同的身份：

- 哪个服务正在调用：`sky-ai-service`
- 这个服务正在代表哪个用户：例如用户`1001`

因此使用两个用途不同的JWT。

#### 第一步：验证用户登录JWT

用户请求AI服务：

```
POST /api/ai/poc/chat
authentication: <user-jwt>
```

AI服务先使用用户JWT密钥验签，然后从可信Claims中读取：

```
{
  "userId": 1001,
  "exp": 1788105600
}
```

请求体不允许提供`userId`，避免用户或模型修改身份。

#### 第二步：签发服务JWT

AI服务调用业务服务前，生成短期服务JWT：

```
{
  "sub": "sky-ai-service",
  "aud": "sky-server",
  "tokenType": "service",
  "iat": 1788105500,
  "exp": 1788105560,
  "jti": "随机唯一值"
}
```

它只证明调用方是AI服务，不携带用户身份。

#### 第三步：签发用户上下文JWT

同时生成另一枚短期JWT：

```
{
  "aud": "sky-server",
  "tokenType": "user_context",
  "userId": 1001,
  "conversationId": "c-123",
  "iat": 1788105500,
  "exp": 1788105560,
  "jti": "另一随机唯一值"
}
```

这枚Token表示：

> `sky-ai-service`本次工具调用是在代表用户1001执行。

两枚JWT使用不同密钥，降低一类Token泄漏后冒充另一类Token的风险。

#### 第四步：携带两个Token调用业务工具

```
GET /internal/ai-tools/users/me/orders/90001/progress
Authorization: Bearer <service-jwt>
X-AI-User-Context: <user-context-jwt>
```

`sky-server`依次检查：

- 两个JWT签名；
- `aud`是否为`sky-server`；
- `tokenType`是否符合用途；
- 服务JWT的`sub`是否为`sky-ai-service`；
- `iat`、`exp`和最大有效时间；
- 必要Claims是否完整。

只有两个Token都验证通过，才把`userId`和`conversationId`写入本次请求上下文。

Controller不接收`userId`参数：

```
Long userId = AiRequestContext.getCurrentUserId();
```

数据库查询继续进行归属限制：

```
SELECT ...
FROM orders
WHERE id = :orderId
  AND user_id = :authenticatedUserId
```

请求完成后清理线程上下文，避免服务器线程复用时将上一个用户的身份带到下一个请求。

这套设计建立了两层信任：

```
服务JWT：你是否是可信AI服务
用户上下文JWT：你本次代表哪个已认证用户
```

### 3. 可能有哪些并发问题？ 注释 3

#### 场景一：同一会话同时发送两条消息

用户快速发送：

```
消息A：推荐几个30元以内的菜
消息B：不要辣的
```

两个请求同时读取：

```
lastSequence = 20
```

如果都计算`20 + 1`，就可能同时写入`sequenceNo=21`，导致：

- 消息顺序冲突；
- 唯一键异常；
- “不要辣的”可能错误关联上一轮上下文。

解决方式是写消息前锁定会话行：

```
SELECT last_message_sequence
FROM ai_conversation
WHERE conversation_id = ?
FOR UPDATE;
```

第一个事务写完并提交后，第二个事务才能获得新的序号。

#### 场景二：网络重试产生两份回复

用户发送消息后，因为网络超时再次提交相同请求：

```
请求1 → 模型生成回复
请求2 → 模型再次生成回复
```

如果没有幂等控制，可能出现：

- 同一用户消息保存两次；
- Agent回答两次；
- 工具调用两次；
- 如果是写操作，可能重复取消订单或重复创建工单。

客户端为每次逻辑请求生成稳定的`clientRequestId`：

```
clientRequestId = req-abc-123
```

服务端为它建立唯一约束。相同幂等键再次提交时，返回已有处理结果，而不是重新执行。

#### 场景三：同一个幂等键被用于不同内容

客户端错误地提交：

```
第一次：
clientRequestId=req-123
message=查询订单A

第二次：
clientRequestId=req-123
message=查询订单B
```

如果只检查幂等键，第二次可能错误返回订单A的结果。

因此还要计算请求指纹：

```
fingerprint = SHA256(
    message +
    orderId +
    其他影响结果的参数
)
```

相同幂等键但指纹不同，应返回冲突错误，不能回放旧结果。

#### 场景四：两个工作线程同时更新助手消息

助手消息最初为：

```
status=PENDING
version=0
```

线程A生成成功，线程B也因为重试或任务重复消费开始处理。它们可能分别写入不同答案。

采用乐观锁：

```
UPDATE ai_message
SET content = ?,
    status = 'COMPLETED',
    version = version + 1
WHERE message_id = ?
  AND status = 'PENDING'
  AND version = 0;
```

只有第一个更新成功。第二个线程受影响行数为0，知道结果已经被其他线程完成，不能覆盖。

#### 场景五：工具被重复执行

如果Agent调用“查询订单”两次，影响通常不大。但未来接入：

- 取消订单；
- 创建工单；
- 添加购物车；
- 发放优惠券；

重复执行就可能造成真实业务副作用。

每次工具调用需要独立幂等键：

```
assistantMessageId + toolName + normalizedArguments
```

业务工具本身也必须实现幂等，不能只依赖Agent层。

#### 场景六：Redis和MySQL上下文不一致

线程A更新MySQL中的偏好：

```
spicyLevel = 0
```

线程B同时更新Redis：

```
maxPrice = 30
```

如果都基于旧上下文整体覆盖，可能丢失其中一个修改。

可以通过以下方式处理：

- 为上下文维护`contextVersion`；
- Redis使用Lua脚本原子更新；
- 采用字段级合并，避免覆盖整个对象；
- MySQL提交后再更新或删除Redis缓存；
- 发现版本或`lastSequence`不一致时，从MySQL重建缓存。

#### 场景七：SSE断线重连导致重复展示

服务端已经发送了事件10，但客户端收到后还没确认连接就断开。重连后服务端可能再次发送事件10。

解决方式是：

- 每个SSE事件使用稳定事件ID；
- 客户端携带`Last-Event-ID`；
- 前端按照事件ID去重；
- 服务端从下一条事件继续发送。

这些机制分别解决不同层面的问题：

| 机制       | 主要解决的问题             |
| ---------- | -------------------------- |
| 会话行锁   | 同一会话消息序号冲突       |
| 幂等键     | 相同请求被重复执行         |
| 请求指纹   | 幂等键被错误复用于不同内容 |
| 乐观锁     | 多线程覆盖同一助手结果     |
| 工具幂等键 | 有副作用的工具被重复调用   |
| 上下文版本 | Redis/MySQL状态相互覆盖    |
| SSE事件ID  | 断线重连后重复展示         |
