# 1时间格式不一致

> 经验总结：
> 本次 TOOL_UNAVAILABLE 并不是端口、JWT、内部密钥或 Redis 异常，而是两个服务的时间格式不一致：
> 纯文本
> ￼
> ￼
> sky-server 返回：2026-08-20 02:44
> sky-ai-service 期望：2026-08-20T02:44:00
> 由于 sky-server 使用 Spring Boot 2.7/Jackson 2，sky-ai-service 使用 Spring Boot 4/Jackson 3，LocalDateTime 默认序列化规则不同，导致 AI 服务反序列化工具结果失败。异常又被统一转换成了 TOOL_UNAVAILABLE，掩盖了真实原因。
> 最终采用最小修复：在 AI 服务的三个时间字段上添加：
> Java
> ￼
> ￼
> @JsonFormat(pattern = "yyyy-MM-dd HH:mm")
> 由此得到的经验是：跨服务 DTO 必须明确约定时间格式，不能依赖不同框架版本的默认行为；同时，统一错误响应应配合原始异常日志和 traceId，方便快速定位问题。

刚才问题的完整总结如下：

1. 用户调用的是正确入口：

```
POST http://localhost:8081/api/ai/poc/chat
```

其中：

- `sky-ai-service`：8081
- `sky-server`：8080

1. 用户 JWT 验证成功，否则不会进入工具调用阶段。
2. `sky-ai-service` 调用 `sky-server` 后，对外返回：

```
{
  "code": "TOOL_UNAVAILABLE",
  "message": "业务信息暂时无法查询，请稍后重试"
}
```

1. 排查确认：
   - 两个服务均正常启动；
   - 8080、8081 均正常监听；
   - 内部接口存在；
   - 两个服务的内部密钥一致；
   - 内部 JWT 签发和验证正常；
   - Redis 中门店状态可以正常查询；
   - 直接调用内部工具能够返回 `200` 和 `OPEN`。
2. 真正原因是时间格式不兼容：

```
sky-server 返回：2026-08-20 02:44
sky-ai-service 默认期望：2026-08-20T02:44:00
```

`sky-server` 使用 Spring Boot 2.7/Jackson 2，并将 `LocalDateTime` 序列化为：

```
yyyy-MM-dd HH:mm
```

`sky-ai-service` 使用 Spring Boot 4/Jackson 3，不能按照默认规则将该字符串反序列化成 `LocalDateTime`。

反序列化异常被 `SkyServerToolClient` 捕获，并统一转换成了 `TOOL_UNAVAILABLE`，所以客户端没有看到真实的时间解析异常。

1. 最小修复是在 AI 服务的三个时间字段上增加：

```
@JsonFormat(pattern = "yyyy-MM-dd HH:mm")
```

涉及：

- `ShopStatus.checkedAt`
- `OrderProgress.estimatedDeliveryTime`
- `OrderProgress.deliveredAt`

没有修改：

- `sky-server`
- 全局 Jackson 配置
- 接口 JSON 格式
- 鉴权逻辑
- 工具调用流程

1. 修改后测试结果：

```
Tests run: 9
Failures: 0
Errors: 0
BUILD SUCCESS
```

最后只需要重启 `sky-ai-service`，然后重新发送 Apifox 请求即可。长期建议把两个服务之间的时间字段统一为 ISO-8601，减少不同 Spring Boot/Jackson 版本之间的兼容问题。
